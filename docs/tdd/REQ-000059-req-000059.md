## 0. Requirement Trace (in lieu of a PRD)

Since REQ-000059 has no PRD, this TDD extracts requirements directly from the GitHub issue body embedded in `state.json.description`. Every design decision below references one of these:

- **BR-1 (sticky cancel):** `request cancel <id> --yes` MUST make the request permanently non-actionable. After cancel, no daemon restart, orphan-reconciliation pass, or portal-marker sweep may re-select or re-activate it.
- **BR-2 (state.json → cancelled):** Cancel MUST persist `status=cancelled` to the on-disk `state.json`. *(Already covered by #551 via `syncTransition`; this TDD re-verifies it and adds regression coverage.)*
- **BR-3 (gate-decision cleanup):** Cancel MUST delete the pending gate-decision file at `${GATE_DECISIONS_DIR}/<repo-basename>__<request-id>.json` so the portal cannot resurrect it as "in gate" and the daemon's approvals-consumer path cannot flip the state back to `gate/<phase>`.
- **BR-4 (tombstone):** Cancel MUST write a tombstone marker inside the request directory (`.autonomous-dev/requests/<id>/cancelled.tombstone`) so ALL reconciliation and recovery paths (bash daemon + TS `ReconciliationManager` + `journal_replay` + `restore_interrupted_session`) can consult a single, canonical sentinel and refuse to overwrite `state.json` from `checkpoint.json` or the SQLite row.
- **BR-5 (queue starvation fix):** A cancelled request MUST NOT hold the single work slot; `select_request` MUST skip it on every subsequent poll, releasing the slot for the next queued request.
- **BR-6 (no scope creep):** No changes outside the failing scope; follow existing test conventions. (From `state.json.acceptance_criteria` / constraints.)

## 1. Overview

This is a bug fix that hardens the request-cancel flow into a **terminal, sticky** operation. The current cancel path updates SQLite + `state.json` atomically (via `handoff_manager.cancelRequest` and `state_sync.syncTransition` — introduced in #551), but three orthogonal resurrection vectors survive:

1. **Checkpoint replay:** `restore_interrupted_session()` in `bin/supervisor-loop.sh` `cp`s `checkpoint.json` over `state.json` unconditionally when a request has `current_phase_metadata.session_active=true`. The checkpoint was written **before** cancel, so it says `gate/code_review` — the daemon overwrites `cancelled` back to `gate/code_review`.
2. **Gate-decision file:** `${GATE_DECISIONS_DIR}/<repo>__<id>.json` (written by `write_gate_decision`) remains on disk. The portal continues to advertise the request as "in gate" and the review-gate CLI/session can be re-attached to it.
3. **Reconciliation / journal replay:** Both the on-startup `journal_replay` (`intake/recovery/journal_replay.ts`) and operator-invoked `ReconciliationManager.repair()` (`intake/core/reconciliation_manager.ts`) will happily rebuild `state.json` from a SQLite row — or worse, push a stale filesystem `status` back into SQLite (`repairContentMismatch` fs-newer branch) if a subsequent write beat the cancel commit by ms.

The **minimum-viable** fix is a **tombstone** — a single 0-byte marker file (`cancelled.tombstone`) written inside the request directory at cancel time. Every code path that could resurrect a request (`select_request`, `restore_interrupted_session`, `journal_replay`, `ReconciliationManager.repair`, `reconcile_portal_markers`, portal action write) checks for the tombstone and short-circuits. This is intentionally lower-tech than modifying the SQLite schema or the `state.json` v1.1 schema — the tombstone is a filesystem-native "do not touch" flag and it survives every code path we can control.

**Design surface:** small but non-trivial. New public sentinel (the tombstone file), new helper in the TS lifecycle handler, new short-circuits in ~6 call sites, and regression tests. Full TDD rigor (API, error handling, testing, ADRs) applies here — this is not a docs edit.

### 2.2 Data flow — cancel to durable terminal state

1. Operator invokes `autonomous-dev request cancel REQ-NNNNNN --yes`.
2. `CancelHandler.execute()` validates state and calls `syncTransition` — this atomically writes SQLite `status='cancelled'` **and** `state.json.status='cancelled'` under a per-request file lock (unchanged from #551).
3. **NEW:** After `syncTransition` resolves `true`, the handler calls `finalizeCancellation(requestId, repoPath)`:
   - `writeCancelledTombstone(requestPath)` — creates `<reqDir>/cancelled.tombstone` (empty file, mode 0o600, `O_CREAT|O_EXCL`; ENOENT/EEXIST tolerated).
   - `deletePendingGateDecision(repoBasename, requestId)` — unlinks `${GATE_DECISIONS_DIR}/<repoBase>__<id>.json` (ENOENT tolerated).
4. Both operations are **best-effort, non-fatal** — a failure logs a warning but does NOT roll back the cancel (SQLite + `state.json` are already `cancelled` and those alone make the request non-actionable to a fresh daemon).
5. Portal ActivityLog + `request_cancelled` event emission proceed unchanged.

### 2.3 Data flow — daemon startup resurrection is prevented

- **`select_request`** (bash) already skips `status=cancelled` via `case ... in done|cancelled|failed|paused) continue`. The tombstone is a defensive, **additional** short-circuit that runs BEFORE the `jq` state.json parse — so even a corrupt/replayed `state.json` cannot be re-selected.
- **`restore_interrupted_session`** (bash): before the `cp checkpoint.json state.json`, check for `cancelled.tombstone`. If present, log a `session_cancelled_skipped` event and RETURN without touching state.json. This is the fix for the primary observed regression.
- **`journal_replay`** (TS): before emitting `STATE_DRIFT` or `RECOVERY_INSERT`, check for `cancelled.tombstone`. If present, emit `CANCELLED_SKIPPED` (new mismatch type) and skip all mutations.
- **`ReconciliationManager.detectDivergence` / `.repair`**: request-level tombstone check. Cancelled requests are always "clean" — no drift is reported, and if a report was already produced, `repair` returns `action='skipped'` with `error_message='request is cancelled (tombstone present)'`.
- **`reconcile_portal_markers`**: the existing logic already refreshes markers when `state.json.status ∈ {done, cancelled, failed}` and removes the gate-decision file. The tombstone check makes this idempotent even when `state.json` is corrupt.

## 3. Detailed Design

### 3.1 The tombstone contract

- **Location:** `<repo>/.autonomous-dev/requests/<REQ-NNNNNN>/cancelled.tombstone`.
- **Content:** empty (0 bytes). Presence-only sentinel. Rationale: any content invites schema evolution and drift; presence is atomically observable via `fs.existsSync` / `[[ -e ... ]]`.
- **Permissions:** `0o600`. Matches `state.json` mode.
- **Lifecycle:** written **after** the two-phase commit of `cancelRequest` succeeds. Never removed by any code path in this change. (Human operators can `rm` it manually if they intentionally want to un-cancel a request — that path is out of scope for this fix and is documented in §11 Open Questions.)
- **Atomicity:** creation uses `O_CREAT|O_EXCL` so a race between two cancel-CONFIRM calls is safe (the second sees `EEXIST` and treats it as success).
- **Idempotency:** `finalizeCancellation` is safe to call repeatedly. `select_request` and reconciliation paths treat "already cancelled" and "just cancelled" identically.

### 3.2 New TS module: `intake/handlers/cancel_finalizer.ts`

```ts
/**
 * Post-commit finalizer for cancel: writes the cancelled tombstone and
 * deletes any pending gate-decision file.
 *
 * MUST run only AFTER syncTransition() resolves successfully — otherwise a
 * SQLite failure would leave a tombstone without a matching db row.
 *
 * All operations are best-effort. Failures are logged (JSON, single line)
 * but MUST NOT throw — the cancel is already durable in SQLite + state.json.
 */

export interface FinalizeCancelOptions {
  /** Absolute request directory (already realpath-resolved). */
  requestPath: string;
  /** Basename of the target repo, used to compose the gate-decision file. */
  repoBasename: string;
  /** REQ-NNNNNN. */
  requestId: string;
  /** Override for tests. Defaults to process env AUTONOMOUS_DEV_STATE_DIR or ~/.autonomous-dev. */
  gateDecisionsDir?: string;
}

export interface FinalizeCancelResult {
  /** True iff the tombstone exists on disk after the call (created or pre-existing). */
  tombstoneWritten: boolean;
  /** True iff the gate-decision file no longer exists after the call. */
  gateDecisionDeleted: boolean;
  /** Non-fatal warnings surfaced to operator logs; empty on the happy path. */
  warnings: string[];
}

export const CANCELLED_TOMBSTONE_BASENAME = 'cancelled.tombstone';

export async function finalizeCancellation(
  opts: FinalizeCancelOptions,
): Promise<FinalizeCancelResult>;

/**
 * Presence check — used by every reconciliation / recovery path. Never
 * throws; a stat error other than ENOENT is treated as "unknown" and
 * returns false (the caller then falls back to its normal check, which is
 * still gated by state.json.status).
 */
export function isCancelledTombstonePresent(requestPath: string): boolean;
```

**Behaviour:**

- `writeCancelledTombstone(requestPath)` → `fs.mkdirSync(requestPath, {recursive:true, mode:0o700})` then `fs.openSync(path.join(requestPath, CANCELLED_TOMBSTONE_BASENAME), O_CREAT|O_EXCL|O_WRONLY, 0o600)` and immediately `close`. On `EEXIST`, return success. On any other error, push to `warnings[]` and continue.
- `deletePendingGateDecision(gateDir, repoBase, id)` → `fs.unlinkSync(<gateDir>/<repoBase>__<id>.json)`. On `ENOENT`, treat as success. On other errors, push to `warnings[]` and continue.
- Default `gateDecisionsDir` resolution mirrors `bin/supervisor-loop.sh` line 34:
  `process.env.AUTONOMOUS_DEV_STATE_DIR ?? path.join(os.homedir(), '.autonomous-dev')` + `/gate-decisions`.

```ts
// db-only fallback path needs the tombstone so future reconciles can't
```

### 3.4 Bash changes in `bin/supervisor-loop.sh`

#### 3.4.1 New helper (near line 800, alongside `select_request`)


#### 3.4.3 `restore_interrupted_session` (line ~493)

Insert at the very top, right after argument binding:

```bash
if is_request_cancelled_tombstoned "${req_dir}"; then
```

### 3.5 Changes in `intake/recovery/journal_replay.ts`

Add a new `JournalMismatchType`: `'CANCELLED_SKIPPED'`. In the `Present-Present` and `Missing-Present` branches, check `isCancelledTombstonePresent(<repo>/.autonomous-dev/requests/<id>)`:

```ts

  mismatches.push({ requestId, type: 'CANCELLED_SKIPPED', details: 'tombstone present' });
  continue; // do NOT update SQLite, do NOT insert
}
```

Also: in the `Missing-Present` (`RECOVERY_INSERT`) branch, if the state.json parses and says `status='cancelled'`, treat as CANCELLED_SKIPPED even without a tombstone — belt-and-suspenders.

### 3.6 Changes in `intake/core/reconciliation_manager.ts`

- **`detectDivergence`:** in both `scanSqliteSide` and `scanFilesystemSide` loops, skip a `request_id` whose request directory contains a `cancelled.tombstone`. Rationale: cancelled requests are terminal — any drift is either intentional (operator wrote `cancelled`) or old checkpoint data we intentionally ignore.
- **`repair`:** at the top of the switch, if `isCancelledTombstonePresent(this.requestDir(report.repository, report.request_id))` returns `true`, return `{ action: 'skipped', error_message: 'request cancelled (tombstone)' }` before dispatching to any category-specific repair. This closes the "fs newer content_mismatch pushes stale fields back to SQLite" hole.

`bin/supervisor-loop.sh` already calls `write_portal_request_action` for terminal-status refreshes; no functional change needed. The tombstone check is added to `reconcile_portal_markers` per §3.4.5.

## 4. API Specification

The only new public API is `cancel_finalizer.ts` (see §3.2). All other changes are internal edits to existing modules whose public signatures are unchanged.

### 4.1 Contract summary

| Symbol | Purpose |
| --- | --- |
| `finalizeCancellation(opts)` | Post-commit finalize: writes tombstone + deletes gate-decision file. Best-effort. |
| `isCancelledTombstonePresent(requestPath)` | Presence check; returns `false` on any stat error other than success. |
| `CANCELLED_TOMBSTONE_BASENAME` | Exported const `'cancelled.tombstone'` so bash and TS agree on the name via a single source of truth (bash reads a hardcoded string but is documented to match this const — see §7 note on schema drift). |

### 4.2 Error semantics

`finalizeCancellation` NEVER throws. All error paths return via `warnings[]`. Callers surface warnings but do not fail the cancel — SQLite + `state.json` are already durable at the point the finalizer runs.

## 5. Data Design

- **New on-disk artifact:** `<repo>/.autonomous-dev/requests/<REQ-NNNNNN>/cancelled.tombstone`. Empty, 0o600.
- **No SQLite schema change.** Rationale: adding a column requires a migration and cross-daemon coordination; the tombstone is filesystem-native and only meaningful during reconciliation, which is filesystem-scoped anyway.
- **No `state.json` schema change.** The v1.1 `StateJsonV11` shape is untouched; `status='cancelled'` already exists in the enum.
- **Gate-decision file:** the format is unchanged; we merely delete it earlier (on cancel instead of only on `phase_advance → completed`).

### 5.1 Migration

- **Existing cancelled requests without a tombstone:** at daemon startup, if `journal_replay` sees a SQLite row with `status='cancelled'` and no tombstone, it creates one (idempotent). This heals in-flight cancels from the previous version without operator intervention.
- **Rollback:** removing the tombstone file is a no-op; the daemon behaves as before the fix. This is safe because `select_request` still filters on `state.json.status` — the tombstone is a defense-in-depth marker, not the primary status signal.

## 6. Error Handling

| Failure | Symptom | Handling |
| --- | --- | --- |
| Tombstone write fails (EACCES/ENOSPC) | Warning logged; cancel still succeeds | Push to `warnings[]`; downstream `state.json.status=cancelled` still causes `select_request` to skip. |
| Tombstone write races with itself | Two concurrent CONFIRM calls | `O_EXCL` returns EEXIST on the loser; treated as success. |
| Gate-decision delete fails (EACCES) | Warning logged; portal may still show stale marker briefly | Push to `warnings[]`; `reconcile_portal_markers` will re-attempt at next sweep. |
| Tombstone present but `state.json` says `running` (corruption) | Reconciliation refuses to change anything | Operator alerted via `journal_replay` `CANCELLED_SKIPPED` mismatch; manual cleanup documented in `docs/RUNBOOK.md` (out of scope for this TDD). |
| Checkpoint exists, tombstone exists, `state.json` corrupt | `restore_interrupted_session` refuses to overwrite | New minimal `state.json` written with `status=cancelled` (§3.4.4). |

## 8. Security Considerations

- **File mode:** tombstone is 0o600 (owner-only). Prevents another local user from planting a spoof tombstone on a shared machine to DoS a valid request. The request directory itself is 0o700, so this is defense-in-depth.
- **Path traversal:** `finalizeCancellation` receives an already-realpath-resolved `requestPath` from the caller (mirrors `handoff_manager`'s protocol). No user-controlled path segments are joined; the tombstone basename is a const.
- **Gate-decision path:** composed from `path.basename(project)` — `basename` strips any traversal. Additional guard: `validateRequestId(requestId)` (already invoked by `resolveRequestPathFromDb` upstream).
- **Race with a live session:** if a session is actively writing `state.json` when cancel is invoked, the per-request `FileLock` (used by `cancelRequest`) serializes them; the tombstone is written after the lock is released, so a stale writer that raced the lock cannot resurrect the state (their write commits `cancelled`, then the tombstone is written).

---

## 9. Performance Considerations

- One extra `fs.openSync + close` per cancel — O(1), negligible.
- Each `select_request` iteration adds one `[[ -e <path> ]]` per request directory — O(N) where N is number of requests scanned. On typical repos (N < 100), this is sub-millisecond.
- `journal_replay` adds one `existsSync` per SQLite row per FS entry pair — same order as existing `readFileSync(state.json)` cost. No measurable impact.

## 10. Architecture Decision Records

### ADR-1 — Use a filesystem tombstone instead of a SQLite column

- **Context (BR-1, BR-4):** Cancel must be sticky across restarts and against multiple reconciliation code paths (bash + TS).
- **Options:**
  1. Add a `cancelled_terminal` boolean to the SQLite `requests` table.
  2. Extend `state.json` v1.1 schema with a `cancel_marker` field.
  3. Filesystem tombstone (`cancelled.tombstone`).
- **Decision:** Option 3.
- **Consequences (+/-):**
  - **+** No SQLite migration; no cross-daemon-version coordination; no `state.json` schema bump.
  - **+** Bash can check it with `[[ -e ... ]]` — no new jq schema.
  - **+** Survives `state.json` corruption (unlike option 2).
  - **+** Survives SQLite reset (a nuke of the intake db still leaves cancelled requests un-resurrected on disk).
  - **−** Operators who manually manipulate request directories must be trained to remove the tombstone if they intend to un-cancel a request. Mitigation: document in `docs/RUNBOOK.md`.
  - **−** One extra filesystem artifact per cancel. Acceptable — cancel is a low-frequency event.

### ADR-2 — Best-effort, non-fatal finalization

- **Context:** Finalization runs after SQLite + `state.json` are already committed as cancelled. If the tombstone write fails, is the cancel still "sticky"?
- **Decision:** Yes; `select_request` already skips `status='cancelled'` from `state.json`. The tombstone is defense-in-depth. Finalization warnings go to logs but never fail the cancel.
- **Consequences:** In pathological edge cases (state.json corrupted between cancel and next restart), the tombstone provides an additional safety net. In normal operation, the tombstone and `state.json.status='cancelled'` are redundant sentinels — either one suffices to prevent resurrection.

### ADR-3 — Journal-replay back-fills tombstones for legacy cancelled rows

- **Context:** Existing cancelled requests from before this change lack tombstones.
- **Decision:** `journal_replay` at startup writes a tombstone for any SQLite row with `status='cancelled'` that lacks one. This is idempotent, cheap, and prevents any "worked before, broken now" surprise after upgrade.
- **Consequences:** One-time O(K) work on first startup after upgrade, where K = number of pre-existing cancelled requests. Typical K < 10.

## 12. Open Questions

1. **Portal UI:** should the portal show a distinct "cancelled" badge distinguishable from "done" when the tombstone is present? Out of scope for this fix — the portal already renders `status='cancelled'` correctly; the tombstone is a daemon-internal marker.
2. **Un-cancel workflow:** operators occasionally want to reverse a cancel. Today's answer: `rm cancelled.tombstone && jq '.status="queued"' state.json > .tmp && mv .tmp state.json && sqlite3 ... UPDATE ...`. A first-class `request uncancel` CLI would be safer but is deferred — not part of this fix's scope (BR-6).
3. **Multi-repo cancel:** `finalizeCancellation` operates on a single (repoBase, id) tuple. If a request was ever mirrored across repos (it isn't, per current architecture), we'd need to iterate. Confirmed non-issue on inspection of `handoff_manager` — `resolveRequestPathFromDb` returns a single path per id.
4. **`journal_replay` back-fill vs. explicit migration script:** we chose in-daemon back-fill for zero-touch upgrade (ADR-3). If operators prefer an explicit script, we can also expose a `autonomous-dev request migrate-tombstones` command; deferred until requested.
