## 2. Overview

REQ-000060 fixes a class of operational silent-failures where a phase
session hangs (as REQ-000057's plan phase did for 39 minutes) and leaves
operators with **zero explanatory data**: an empty 0-byte transcript, no
progress markers, no historical-baseline anomaly signal, and no
diagnostic capture at kill or timeout time. The design ships four
cooperating pieces, all additive and default-on with safe fallbacks:

1. **Streamed + flushed transcripts.** `dispatch_phase_session()`
   currently uses `bash spawn-session.sh ... > "${output_file}" 2>&1`
   which relies on stdio being flushed before exit. When the child
   hangs mid-turn, kernel buffering can leave the file at 0 bytes —
   the exact worst-case pathology in issue #635. Replace with a
   line-buffered pipe → `tee -a` combination (`stdbuf -oL -eL` on the
   child, `tee -a "${output_file}"` on the pipeline receiver) so every
   line the agent emits is on disk **before** the next tool call.
2. **Per-session liveness heartbeat.** A daemon-side sidecar writes
   `session-progress.json` in the request directory every N seconds
   with `{ ts, elapsed_ms, transcript_bytes, transcript_last_mtime,
   delta_bytes_last_interval, session_pid, phase }`. The sidecar is
   driven from the same subshell that spawns the session; it exits
   when the session exits (SIGCHLD or the completion sentinel). No new
   long-lived process is introduced.
3. **Early anomaly detection.** A pure detector reads the heartbeat +
   `~/.autonomous-dev/state/observability/phase-baselines.json` (a
   rolling p50/p95 per phase — bootstrapped lazily; empty file is
   valid) and fires a `session_hung_suspected` event when EITHER
   (a) elapsed > `anomaly_multiplier` × phase p95 OR (b) transcript
   has emitted no bytes for `silent_stall_seconds`. This fires
   **well before** the hard timeout (default 1h) — targets are `k=3.0`
   and `silent_stall_seconds=300`. Both parameters live in
   `plugins/autonomous-dev/config/defaults.json` under
   `observability.hung_session.*`.
4. **Diagnostic snapshot on stuck-detection / kill / timeout.** A pure
   snapshotter dumps a machine-readable `session-stuck-<ts>.json` file
   into the request dir containing: ps line for the session PID,
   `lsof -p` (network + open FDs — key signal for an API stall vs a
   deadlocked disk I/O), tail of the (now non-empty) transcript,
   elapsed-since-last-output, current phase / agent, and the last two
   heartbeat samples. The snapshotter is invoked from three call
   sites (anomaly-detected → advisory snapshot; SIGTERM/kill delivered
   → post-mortem snapshot; wall-clock timeout branch in
   `dispatch_phase_session` → post-mortem snapshot). Every snapshot
   also emits a `session_stuck` event in `events.jsonl`.

All four pieces integrate into the *existing* dispatch path in
`plugins/autonomous-dev/bin/supervisor-loop.sh::dispatch_phase_session`
(§4.1 below); no new daemon, no new process manager. The heartbeat +
detector run in-band inside the same subshell already gated by
`timeout`/`gtimeout`, so a heartbeat failure can never wedge the
supervisor.

The change is deliberately conservative on control flow:

- We do **not** replace the current wall-clock timeout — that path
  (line 1907 of `supervisor-loop.sh`) still fires at the hard ceiling
  and remains the ultimate guard. Anomaly detection is *additive*: it
  emits an event and dumps a snapshot but does not kill the session
  by itself in v1. Killing on anomaly is deferred to a follow-up
  (see §12 T7) once operators have a week of empirical
  false-positive data.
- We do **not** touch `dispatch_agent` semantics for existing agents,
  transcripts, or `phase-result-<phase>.json` synthesis.
- We do **not** change the `--print --output-format json` claude
  invocation; `stdbuf`-based line buffering is applied at the OS pipe,
  not the claude CLI.

### 3.3 Data Flow (single dispatch, happy path)

1. `dispatch_phase_session` computes `output_file =
   ${req_dir}/session-${epoch}.txt` (unchanged).
2. `progress_file = ${req_dir}/session-progress.json`; touch it with an
   initial `{status: "starting"}` record.
3. `phase_start_ms = date +%s%3N`; snapshot the working tree.
4. Spawn subshell:
   - Start the heartbeat sidecar (§4.3) in background with `progress_file`,
     `output_file`, `phase`, `phase_start_ms`, and `session_pid_slot`
     (a file that the pipeline writes `$!` to after fork).
   - Run: `stdbuf -oL -eL bash spawn-session.sh <state> <phase> <agent> <prompt> 2>&1 | tee -a "${output_file}" > /dev/null`;
     capture `${PIPESTATUS[0]}` as the effective session exit code.
   - Kill heartbeat sidecar (`kill $HB_PID 2>/dev/null || true`); wait for it.
5. On `exit_code == 124` OR `exit_code == 125` (existing branches):
   - Emit post-mortem `session_stuck_snapshot.sh` with reason
     `hard_timeout` / `soft_timeout_with_progress`.
6. On any exit, if `session-progress.json` shows the detector previously
   emitted `session_hung_suspected` at least once but the session ended
   in success (exit_code == 0, `phase-result-*.json` exists with
   status==pass), also emit a `session_recovered_after_stall` event
   (nice-to-have; §7 error taxonomy).
7. Feed `elapsed_ms = now - phase_start_ms` into
   `phase_baselines.sh::record_sample(phase, elapsed_ms, exit_code)`.
8. Return `${exit_code}|${session_cost}|${output_file}` as today.

### 3.4 Threading, Concurrency, Locking

- The heartbeat sidecar runs in the same subshell as the pipe; when
  the pipe exits, the sidecar's `wait`/`sleep` loop is interrupted by
  a `SIGTERM` sent by `trap EXIT`. No new process manager; nothing
  outlives `dispatch_phase_session`.
- `phase-baselines.json` writes use the same `.tmp.<pid>.<rand> +
  rename` pattern as `trigger_store.ts` / other state files (mode
  `0o600`, parent dir `0o700`). Multiple concurrent dispatches
  (parallel requests) contend on a `phase-baselines.json.lock` file
  taken via `openSync('wx')` semantics (bash: `set -o noclobber` +
  `> "$lock"` idiom). Lock held ≤5 ms per record — negligible.
- `session-progress.json` is per-request (path `<req_dir>/session-progress.json`)
  so parallel requests never touch the same file. It's overwritten in
  place; readers are advised to tolerate torn reads (retry once on
  parse failure).
- `session-stuck-<iso>.json` filenames include an ISO-8601 timestamp
  with millisecond precision to guarantee uniqueness across advisory
  vs post-mortem snapshots within one session.

### 3.5 Invariants

- **INV-1.** `session-<epoch>.txt` grows monotonically while the child
  is emitting — a hang leaves the *partial* transcript intact, never
  0 bytes, IFF the child has emitted at least one line.
- **INV-2.** `session-progress.json` exists from `phase_start_ms + 1`
  onward and is refreshed at least every `heartbeat_interval_seconds`
  (default 15). Absence beyond that window itself indicates the
  supervisor died, not the child — a distinct failure mode.
- **INV-3.** Every `session_hung_suspected` event has a matching
  `session-stuck-*.json` on disk, produced synchronously before the
  event is emitted. Ordering is ledger-first — same rationale as
  ADR-005 in the REQ-000057 TDD.
- **INV-4.** When `AUTONOMOUS_DEV_OBSERVABILITY=0` the code path is
  byte-for-byte identical to today: no sidecar, no `tee`, no
  baselines. This is the compat escape hatch for operators debugging
  the observability itself.

### 4.2 `lib/observability/session_transcript.sh` (streamed transcript)

```bash
# run_streamed_session(timeout_bin, timeout_secs, spawn_script,
#                      state_file, phase, agent, prompt, output_file) -> exit
#
# Runs the spawn script with line-buffered stdout/stderr and tees to
# ${output_file}. Returns the spawn script's exit code via PIPESTATUS.
#
# Line-buffering: `stdbuf -oL -eL` forces libc to flush on newline; the
# claude CLI's own stdio is line-oriented (--output-format json prints
# one JSON blob after each turn), so this is sufficient — no PTY needed.
#
# Portability: On macOS `stdbuf` is Homebrew `coreutils` (as
# `gstdbuf`). Detection: `command -v gstdbuf || command -v stdbuf`.
# When neither exists, run WITHOUT stdbuf but STILL through tee — the
# transcript is at least never 0-byte on flush, only per-turn.
run_streamed_session() {
    local timeout_bin="$1" timeout_secs="$2" spawn_script="$3"
    local state_file="$4" phase="$5" agent="$6" prompt="$7"
    local output_file="$8"

    local stdbuf_bin
    stdbuf_bin=$(command -v gstdbuf || command -v stdbuf || true)

    local -a runner=()
    if [[ -n "${timeout_bin}" ]]; then
        runner=("${timeout_bin}" --kill-after=10s "${timeout_secs}")
    fi
    if [[ -n "${stdbuf_bin}" ]]; then
        runner+=("${stdbuf_bin}" -oL -eL)
    fi
    runner+=(bash "${spawn_script}" "${state_file}" "${phase}" "${agent}" "${prompt}")

    "${runner[@]}" 2>&1 | tee -a "${output_file}" > /dev/null
    return "${PIPESTATUS[0]}"
}
```

Contract:
- `tee -a` guarantees each newline-terminated line is `write(2)`-flushed
  to `output_file` before the next line is read from the pipe.
- `set +o pipefail` is deliberately NOT used here — the caller sets it
  in the wrapping subshell.
- The `runner` array pattern is bash-3.2 safe (macOS system bash), same
  discipline as `spawn-session.sh` §227.

### 4.3 `lib/observability/session_heartbeat.sh`

```bash
# heartbeat_start(req_dir, output_file, progress_file, request_id,
#                 phase, phase_start_ms) -> pid (bg)
#
# Forks a background loop that every ${HB_INTERVAL_S} seconds:
#   1. stat the output_file → bytes, mtime
#   2. compute delta_bytes vs last sample, silent_seconds vs last mtime
#   3. write progress_file atomically (tmp + rename, mode 0600)
#   4. invoke hung_session_detector.sh::detect_hung
#   5. if verdict==suspected → session_stuck_snapshot.sh --advisory + emit event
#   6. sleep ${HB_INTERVAL_S}
# Terminates on SIGTERM (delivered by heartbeat_stop) or when the parent
# subshell exits.
heartbeat_start() { ... echo "$!"; }

heartbeat_stop() {
    local pid="$1" progress_file="$2"
    kill -TERM "${pid}" 2>/dev/null || true
    wait "${pid}" 2>/dev/null || true
    # Final sample: "status=exited"
    _heartbeat_write_sample "${progress_file}" "exited"
}
```

Config surface (env, with defaults from `config/defaults.json`):

| Var | Default | Meaning |
|---|---|---|
| `AUTONOMOUS_DEV_HB_INTERVAL_S` | 15 | seconds between heartbeat samples |
| `AUTONOMOUS_DEV_HB_SILENT_STALL_S` | 300 | seconds of transcript silence → suspected |
| `AUTONOMOUS_DEV_HB_ANOMALY_MULTIPLIER` | 3.0 | elapsed / phase_p95 threshold |
| `AUTONOMOUS_DEV_HB_MIN_BASELINE_SAMPLES` | 5 | fewer samples than this → skip multiplier check |
| `AUTONOMOUS_DEV_OBSERVABILITY` | 1 | master OFF switch |

```jsonc
  "recovery_hint": "silent_stall for ~35m with an open TCP FD to api.anthropic.com:443 → likely API stall; consider retry."
}
```

Robustness:
- Every collection step (`ps`, `lsof`, transcript-tail) is guarded and
  writes `null`/`"unavailable"` sentinels on failure. The snapshot MUST
  land even when `lsof` is unavailable (common in stripped Docker
  images) — a partial snapshot is infinitely better than the current
  zero-byte void.
- `lsof -p <pid>` output is capped at 200 rows (`lsof_truncated: true`
  when hit). Sanitization strips leading path components of anything
  under `/Users/*/private/` (macOS keychain paths).
- Transcript tail is `tail -c 65536 | head -n 128` — bounded even for
  giant transcripts.
- `recovery_hint` is a small rule table (see §7.3) that translates
  `{reason, has_network_fd, has_open_transcript_write}` → a
  human-readable suggestion. Deterministic; no LLM in the loop.

### 4.7 `lib/observability/observability_events.sh`

Thin typed wrappers around `event_append` (the existing sink at
`plugins/autonomous-dev/lib/state/event_logger.sh`). Each emits a valid
JSON payload for the corresponding schema.

```bash
emit_session_hung_suspected(request_id, phase, reason, evidence_json)
emit_session_stuck(request_id, phase, snapshot_path, reason)
emit_session_recovered_after_stall(request_id, phase, suspected_count)
```

**Important compat note.** `event_logger.sh` today accepts a fixed enum
of 25 event types (§17 of `event_logger.sh`). Since the enum is
enforced, we extend it in this PR to include the three new types
(`session_hung_suspected`, `session_stuck`, `session_recovered_after_stall`).
The enum extension is an additive change and does not remove any
existing value.

### 4.8 `bin/spawn-session.sh` — minimal change

No functional change. We introduce **no** new arguments and no new
environment consumption. The child stays unaware of the heartbeat and
tee; observability is applied *around* it. This is the deliberate
low-blast-radius choice — the existing 39 minutes of `spawn-session.sh`
logic (audit hooks, verification, envelope synthesis) is untouched.

The only reason spawn-session appears in the file list is that its
existing script requires no changes but MUST print at least one line at
startup (agent version banner) for the transcript to be non-empty even
if claude itself hangs on the first turn. Verify it does today; if it
doesn't, add a single startup log line at the top of
`spawn_session_typed()` — one line, no branching.

## 6. Data Design

### 6.1 Baseline file (persistent, per-machine)

Path: `~/.autonomous-dev/state/observability/phase-baselines.json`
Mode: `0o600`, parent dir `0o700`.
Schema: see §4.5.

**Migration.** No migration required — first write creates the file
lazily. `schema_version: 1`; future migrations gated by that field.

### 6.2 Progress file (per-request, ephemeral)

Path: `<req_dir>/session-progress.json`
Mode: `0o600`.
Lifecycle: created at dispatch start; refreshed every
`heartbeat_interval_seconds`; last update carries `status: "exited"`.
Retained on disk after the request finishes for post-hoc debugging
(no active cleanup in v1; the existing `.autonomous-dev/requests/`
sweeper handles it with the other per-request files).

### 6.3 Stuck snapshot files (per-request, ephemeral, append-only)

Path: `<req_dir>/session-stuck-<iso>.json`, one file per snapshot event.
Mode: `0o600`.
Retention: same as the rest of the request dir; not otherwise trimmed.
Multiple snapshots per session are permitted (advisory during, one
post-mortem after).

### 6.4 Transcript (per-request, existing)

Path: `<req_dir>/session-<epoch>.txt` (unchanged).
Change: written via `tee -a` from a pipe rather than shell `>`
redirection. Ownership and mode preserved by tee. Existing readers
(operator `cat`, self-heal telemetry) are unaffected because the file
path and format (agent stdout+stderr) do not change.

### 6.5 Events (existing sink)

Path: `<req_dir>/events.jsonl` via `event_append` (unchanged).
Change: three new `event_type` values added to the enum in
`event_logger.sh::VALID_EVENT_TYPES`. This is the only file outside
`lib/observability/` and `bin/supervisor-loop.sh` that changes.

## 7. Error Handling

### 7.1 Error taxonomy

| Code | Where | Handling |
|---|---|---|
| `HB_INTERVAL_INVALID` | `session_heartbeat.sh` on non-integer env | Fall back to default 15 s; log warning; no event |
| `HB_WRITE_FAILED` | atomic write on `session-progress.json` | Skip this tick; continue loop; log warning |
| `SNAPSHOT_LSOF_UNAVAILABLE` | `lsof` binary missing / EPERM | Write `"session.open_fds": [], "session.lsof_error": "unavailable"`; snapshot still lands |
| `SNAPSHOT_PS_UNAVAILABLE` | `ps -p` returns nonzero | Write `"session.ps_line": "unavailable"`; snapshot still lands |
| `SNAPSHOT_WRITE_FAILED` | tmp+rename to `session-stuck-*.json` fails | Log to stderr; emit `session_stuck` event without `snapshot_path`; do NOT block dispatch |
| `BASELINE_LOCK_BUSY` | lock file busy > 500 ms | Skip recording this sample; log warning; next dispatch retries |
| `BASELINE_CORRUPT` | JSON parse fails on load | Preserve corrupt file as `phase-baselines.json.corrupt-<ts>`; reset in-memory to empty; emit warning |
| `EVENT_TYPE_REJECTED` | event_logger enum missed the new types | Impossible after the enum patch lands, but guarded: if `event_append` returns 1 with "invalid event_type", log to stderr and continue |

### 7.2 Recovery flow

- The supervisor loop **must not fail** because observability failed.
  Every observability call site in `dispatch_phase_session` is wrapped:
  `stuck_snapshot ... || true`, `phase_baselines_record ... || true`,
  etc. This is the same discipline as the audit-hook block in
  `spawn-session.sh` (§L268: "observability MUST NOT break the
  pipeline").
- On heartbeat sidecar crash, the main pipe is unaffected. The next
  session snapshot (post-mortem, at exit) will note "no heartbeat
  samples captured" via the `heartbeat.last_two_samples: []` field.

### 7.3 `recovery_hint` rule table (deterministic)

| `reason` | `has_network_fd` | `has_open_transcript_write` | Hint |
|---|---|---|---|
| `silent_stall` | true | true | "API stall likely; consider retry after cool-off" |
| `silent_stall` | false | true | "Agent is spinning without I/O; consider raising log verbosity" |
| `silent_stall` | true | false | "Session stalled with transcript closed; check for output redirect issues" |
| `elapsed_over_p95` | * | * | "Phase running >Nx historical p95; not necessarily hung — inspect transcript tail" |
| `hard_timeout` | * | * | "Wall-clock timeout reached; see phase_baselines to tune timeout" |
| `agent_exited_nonzero` | * | * | "Agent exited without phase-result; check transcript tail for error line" |

Applied purely from data already in the snapshot. No LLM. No I/O beyond
the snapshot itself.

### 7.4 User-facing error messages

- `observability list-stuck`: prints `No stuck sessions found.` when
  empty; never errors on empty.
- `observability show-stuck <bad-path>`: prints
  `snapshot not found: <path>` to stderr, exit 1.
- `dispatch_phase_session` NEVER surfaces observability errors to the
  operator through the normal channel — they land only in
  `events.jsonl` and stderr. This preserves the existing dispatch UX.

## 8. Testing Strategy

### 8.1 Unit tests (bats)

Under `plugins/autonomous-dev/tests/bats/`:

- **`session_transcript_streamed.bats`** — spawn a fake agent
  (`printf 'line1\n'; sleep 3; printf 'line2\n'`) through
  `run_streamed_session`; assert `output_file` contains `line1` at
  T+1s (i.e., BEFORE the child exits). Regression for the 0-byte
  pathology.
- **`session_heartbeat_progress.bats`** — start a fake agent that
  writes 100 bytes/s for 5 s; assert `session-progress.json` contains
  at least 3 samples with monotonically increasing `elapsed_ms` and
  `transcript.bytes`.
- **`hung_session_detector_anomaly.bats`** — table-driven:
  - `elapsed_ms=1000, p95=100000, silent_s=0, threshold=3.0` → ok
  - `elapsed_ms=350000, p95=100000, silent_s=0, threshold=3.0` → suspected (elapsed_over_p95)
  - `elapsed_ms=1000, p95=100000, silent_s=400, stall_s=300` → suspected (silent_stall)
  - `elapsed_ms=350000, p95=null (0 samples), silent_s=0` → ok (baseline cold)
- **`session_stuck_snapshot_shape.bats`** — invoke `stuck_snapshot`
  against a fake session; assert JSON conforms to
  `session-stuck.schema.json` (via `ajv` if available, else jq
  shape checks); assert `lsof_error` and `ps_line` graceful degradation
  when the pid does not exist.
- **`phase_baselines_rolling_update.bats`** — feed 300 samples;
  assert `samples_ms.length == 200` (cap), assert `p50_ms` and `p95_ms`
  are within ±5% of a jq-computed reference over the last 200.

### 8.2 Integration test (bats E2E)

- **`dispatch_phase_session_stuck_e2e.bats`** — the acceptance-critical
  test. Uses a fake spawn-script that:
  1. prints `starting phase <phase>`
  2. sleeps 2 s
  3. prints one more line
  4. sleeps 60 s (simulates a hang past `silent_stall_seconds=5` config
     override)
  5. exits 0
  Override `AUTONOMOUS_DEV_HS_SILENT_STALL_SECONDS=5,
  AUTONOMOUS_DEV_HB_INTERVAL_S=1`, then invoke
  `dispatch_phase_session`. Assert:
  - `session-<epoch>.txt` size > 0 at T=3s and grows to include both

  - At least one `session-stuck-<iso>.json` exists in the request dir.
  - `events.jsonl` contains one `session_hung_suspected` event

This test IS the acceptance-criterion reproduction the state file

## 9. Security Considerations

- **File permissions.** Every new file created (`phase-baselines.json`,
  `session-progress.json`, `session-stuck-*.json`) is `0o600` with
  parent dir `0o700`. Matches the discipline of the existing state
  files.
- **PII / secret leakage.** The snapshot's `session.open_fds` list is
  filtered:
  - Any FD whose `name` matches a keychain / homebrew secret store
    path (`/Users/*/private/`, `/Library/Keychains/`) is redacted to
    `"<redacted>"`.
  - Any FD to a socket with a private-IP peer (RFC1918) is preserved
    (useful debug info); public IPs / hostnames are preserved
    (needed for API-stall diagnosis).
- **Transcript tail** already exists on disk and is not further
  redacted here — the tail is a subset of an existing file with
  identical permissions. No secret bypass is introduced.
- **`ps` output.** Command-line args of the agent process are already
  visible to any user on the host via `ps -ef`; the snapshot captures
  no *new* information, only preserves it at hang time.
- **No new tokens, no new network calls.** Observability is entirely
  local. No exfiltration path is added.
- **Event injection.** All event payloads pass through the existing
  `event_append` validator which enforces the enum and required
  fields. The enum extension adds three well-known values only.

## 10. Performance Considerations

- **Heartbeat sidecar cost.** One `stat` + one `jq` + one small
  `printf` per tick. Measured at ~2 ms/tick on macOS/M1; with the
  default 15 s interval this is < 0.02% CPU. Negligible.
- **Detector cost.** Pure jq arithmetic; ≤1 ms/tick.
- **`stdbuf` overhead.** Line-buffering vs block-buffering costs one
  extra `write(2)` per line. For an agent averaging ~200 lines of
  JSON per phase, that's ~200 extra syscalls per session — < 1 ms
  aggregate.
- **`tee` overhead.** One additional `read`/`write` per line. Same
  order as `stdbuf` — sub-millisecond aggregate.
- **Baseline write cost.** Rolling window is capped at 200 samples;
  jq recomputes p50/p95 in O(n log n) ≈ 1 ms. Lock acquisition <5 ms.
  Aggregate <10 ms per dispatch. Vs a 3-minute phase, negligible.
- **Snapshot cost.** `lsof -p <pid>` is the most expensive step
  (50–200 ms on macOS). Only invoked on advisory or post-mortem — not
  the hot path.
- **Disk footprint.** `session-progress.json` ≤2 KB, refreshed in
  place; `session-stuck-*.json` ≤50 KB each, typically 0–1 per
  request. `phase-baselines.json` bounded at ~250 KB total.
- **When observability is OFF** (`AUTONOMOUS_DEV_OBSERVABILITY=0`),
  the code path is byte-for-byte identical to today. Zero overhead
  regression risk for operators who disable it.

## 11. Architecture Decision Records

### ADR-001 — In-process sidecar vs external `daemon-progress` service

- **Context.** Something needs to write heartbeats and run the detector.
- **Options.**
  1. Background subshell inside `dispatch_phase_session`.
  2. A separate long-lived daemon (`autonomous-dev progress-daemon`).
  3. Push to the existing supervisor loop's tick.
- **Decision.** Option 1.
- **Consequences.** Zero new process lifecycle; sidecar dies with the
  dispatch subshell; parallel dispatches each get their own sidecar
  (correctly isolated by req_dir). No install-time surface change.
- **Rejected.** Option 2 adds a new install artifact + failure mode
  (what if the daemon dies?). Option 3 couples heartbeat cadence to
  the supervisor tick (currently variable), which is exactly what we
  want to decouple.

### ADR-002 — `tee` vs PTY vs `unbuffer` for streaming

- **Context.** Kernel/libc buffers can leave `>` redirection with a
  0-byte file on hang.
- **Options.**
  1. `stdbuf -oL -eL` + `tee -a` (chosen).
  2. `script`/`expect`/`unbuffer` PTY wrapping.
  3. Change claude CLI itself to fflush.
- **Decision.** Option 1.
- **Consequences.** Zero new deps on Linux (`coreutils`); on macOS
  requires Homebrew `coreutils` (already assumed by other plugin
  code). PTY-based approach would work everywhere but pulls in a TTY
  emulation layer and can confuse the claude JSON output mode.
- **Fallback.** When `stdbuf`/`gstdbuf` is absent, degrade to
  `tee`-only (per-turn flushing, still no 0-byte pathology).

### ADR-003 — Anomaly detection emits events, does NOT kill (v1)

- **Context.** Should the detector kill the session on `suspected`, or
  merely emit?
- **Options.**
  1. Emit-only in v1 (chosen).
  2. Kill on suspected.
- **Decision.** Emit-only. Gate `kill_on_anomaly` config key remains
  `false` until we have a week of production data on false-positive
  rate.
- **Consequences.** No new failure mode introduced. Follow-up ticket
  (§12 T7) to flip once data supports it. Aligns with #620's
  self-healing philosophy of "detect, then decide" rather than
  reflex-kill.

### ADR-004 — Baseline as rolling window vs EWMA

- **Context.** How do we track "phase p95"?
- **Options.**
  1. Rolling window of last N samples (chosen).
  2. Exponentially-weighted moving average.
- **Decision.** Rolling window (N=200). p95 is well-defined and
  intuitive for operators. EWMA of a percentile is not a standard
  primitive and is easy to get wrong.
- **Consequences.** Trivial jq math; O(n log n) sort per record.
  Bounded file size. Ignore-124 rule prevents the hard timeout from
  poisoning the tail.

### ADR-005 — Baseline file per-machine, not per-repo

- **Context.** Where does `phase-baselines.json` live?
- **Options.**
  1. `~/.autonomous-dev/state/observability/phase-baselines.json`
     (chosen).
  2. `<repo>/.autonomous-dev/state/observability/phase-baselines.json`.
- **Decision.** Per-machine (~).
- **Consequences.** Baselines aggregate across every request the
  operator runs — larger n, more stable p95. Cross-repo bias is
  acceptable at phase granularity since phase semantics are
  cross-project. Per-repo can be added in v2 if a customer needs it.

### ADR-006 — Extend `event_logger.sh` enum vs new events sink

- **Context.** The existing `VALID_EVENT_TYPES` enum will reject
  unknown types.
- **Options.**
  1. Add three new types to the enum (chosen).
  2. Bypass validation for observability events.
- **Decision.** Add to the enum. Additive and safe.
- **Consequences.** One additional test asserts the enum contains
  the three new values.

### ADR-007 — Snapshot format is JSON, not human-only text

- **Context.** Operators need to skim; ops tools need to parse.
- **Options.**
  1. Structured JSON (chosen), rendered by `observability show-stuck`.
  2. Free-form text log.
- **Decision.** JSON. `show-stuck` handles the pretty-print for
  humans; ops tools consume the raw file.

## 13. Open Questions

- **OQ-1.** Should T7's `kill_on_anomaly` flag flip to `true` in a
  follow-up? Recommendation: run a week with the emit-only default,
  aggregate `session_hung_suspected` counts vs actual hangs, then
  decide. Depends on operator tolerance for false positives.
- **OQ-2.** Should `phase-baselines.json` be per-agent as well as
  per-phase? E.g., `code_review` vs `code` might have wildly different
  distributions. Recommendation: v2 — start with per-phase, split
  when data supports it.
- **OQ-3.** Where does the E2E test's fake agent live? Recommendation:
  `plugins/autonomous-dev/tests/bats/fixtures/fake-agents/` — matches
  existing convention (`fixtures/` already exists for other bats
  tests).
- **OQ-4.** `stdbuf` on macOS is `gstdbuf` via Homebrew coreutils. The
  plugin already assumes several coreutils tools (`gtimeout`). Is the
  fallback path (no stdbuf → tee-only) acceptable, or should we
  hard-require coreutils and fail install without it? Recommendation:
  keep the graceful fallback; hard-requiring is a bigger conversation.
- **OQ-5.** Do we need retention on `session-stuck-*.json` files?
  Recommendation: none in v1 — they land inside `.autonomous-dev/requests/<REQ>/`
  which is already subject to the existing sweeper. A per-file mtime
  purge (e.g., > 30 days) is trivial to add later.
